# 模式交换（dsh-mode-exchange）

## 这个插件解决什么问题

DSH 里「Agent 模式」（Standard / PTC / Code / Research …）在会话**启动那一刻**就固化成一份插件组合：
宿主把该模式的插件装进会话自己的作用域，之后这个会话就一直跑这套组合。
`agentPresets.select()` 只对「还没开始第一轮」的会话有效，已有消息的会话会被
`agent-preset/locked` 挡回来；`recompose()` 也要求 Agent 是空白的。

结果就是：一个跑了很久的会话，你想把它变成 PTC 模式，官方路径只有「新建一个会话」。
这个插件提供两条互补的路：

| 能力 | 命令 | 本质 | 代价 |
| --- | --- | --- | --- |
| **A. 运行时软切换** | `/switch-mode <模式>` | 换系统提示词 + 按会话拒绝旧工具 + 补挂新工具 | 会话 ID 不变，历史连续；但**不是**真正的模式装配 |
| **B. 迁移重建** | `/migrate-session --mode <模式>` | 导日志 → 按新模式建新会话 → 把日志作为原生事件序列导入 | 真模式；但换了一个会话 ID，旧会话默认归档 |

两条路都能在侧栏「模式迁移」面板里点出来，也可以在插件设置页改默认值。

---

## A. 软切换到底做了什么

一次 `/switch-mode ptc` 会在**当前会话的作用域内**做三件事，全部可回退：

1. **换系统提示词。** 在 `system-prompt/assemble` 瀑布里把现有全部 section 摘掉，
   换成一条本插件生成的、描述目标模式（包含它的工具清单与工作方式）的 section。
2. **按会话拒绝旧工具。** `agent.ctx.tools.restrict({ deny })` 把「当前模式有、目标模式没有」
   的工具从**声明与派发两侧**一起去掉——模型看不到它们，调用也会被拒绝。
   这个限制挂在会话自己的作用域层，只影响这一个会话。
3. **补挂新工具。** 「目标模式有、当前模式没有」的工具，用 `agent.ctx.tools.register()`
   注册进会话作用域，`when` 门控保证只在这个会话可见。

另外挂了一道 `tools.guard` 作为兜底防线，防止有别的路径绕开 schema 直接派发。

**入口快照**写在 `<数据目录>/state/switches.json`，所以即使改设置触发了插件重建
（`apply` 重新跑一遍），切换状态也会被读回来重建。`/switch-mode --revert` 撤销以上全部改动。

### 为什么叫「软」切换

| | 真模式装配（新建会话） | 本插件的软切换 |
| --- | --- | --- |
| 插件组合 | 按预设声明挂载 | 不变，只改提示词与工具可见性 |
| 工具执行器 | 由预设决定（native / PTC） | **不变**。PTC 的 `run_code` 传输层不会因为切换而出现 |
| 会话 ID | 新的 | 不变 |
| 历史 | 复制过去 | 原地保留 |
| 子代理 / 团队 | 按新预设 | 不变 |

所以：**如果目标模式的差别只在「有哪些工具、提示词怎么写」，软切换是够用的；
如果差别在工具怎么被执行（PTC 的代码执行通道就是这一类），软切换只能做到「看起来像」，
真正要那种行为请用能力 B。** 面板和命令返回里都会原样告诉你这一点，不会假装成功。

## B. 迁移重建的七个步骤

```
① 导出   ── 会话日志 → <导出目录>/exports/<时间戳>-<短ID>.jsonl（+ .meta.json，含 sha256）
② 校验   ── 行行可解析 / 事件数一致 / seq 从 0 连续 / sha256 匹配；失败即中止，现场保留
③ 建会话 ── 以目标模式作为 agentPreset 创建新会话，并挂载该模式的插件组合
④ 导入   ── 把导出的原生事件序列作为新会话的 constructor seed 写进去（不是「复述一遍」）
⑤ 团队   ── 若 --team on，对新会话的根 Agent 调用 agentTeams.setEnabled(true)
⑥ 归档   ── 若 --delete-old true，先备份再归档旧会话（见下）
⑦ 报告   ── 新旧会话 ID、日志路径、消息数、团队状态、旧会话处置、耗时、逐步时间线
```

### ④「导入」是真导入

新会话的构造函数接受 `(seed, header, inheritedEventCount)`，宿主自己的 fork 通道就是这么用的。
本插件照同样的规则构造 seed：

```
源事件前缀（seq 0..N-1）
  + 一条 session/end-seed{inherited:true} 标记（正好落在 index = inheritedEventCount）
  + 若干「收尾事件」：把源会话里没闭合的 turn/step 补上 step/end、turn/end，
    并给没拿到结果的工具调用造一条 isError 的 tool/result
```

这样新会话读到的历史就是**真正的消息序列**：用户消息、助手消息、工具调用与结果都在，
模型可以像对话从未中断一样继续。未闭合的工具调用会被标注成
`TOOL_OUTCOME_UNKNOWN` / `TOOL_NOT_STARTED`，并把宿主原文的提示语带给模型
（「可能已产生副作用，别盲目重试」）。

### ⑥「删除」的真实含义是「归档」

**DSH 没有删除会话的 API。** 工作区服务只有 `archiveSession` / `unarchiveSession` / `pinSession`；
`workspaceRegistry.delete()` 删的是**工作区**，不是会话。

所以这里的「删除旧会话」= 归档：

- 会话从所有分组界面隐藏，并从置顶列表移除；
- 若配置或调用方要求，会先停掉它的活动；
- **磁盘上的会话日志文件仍然存在**，可以用 `unarchiveSession` 反悔。

差异之所以重要：如果你期待「数据被抹掉」，归档做不到；如果你期待的是
「它别再出现在我的会话列表里」，归档正好。报告里会明确写「已归档」而不是「已删除」。

此外，删除这一步**可能延后**：`/migrate-session` 是跑在旧会话的 Agent 里的，
当场归档自己会打断正在进行的工作。所以实现是「先尝试停掉活动再归档；若宿主要求当前回合结束后才能停，
就排到微任务里重试」，并如实标记为「已排期」。

## 安全边界

- **作用域**：能力 A 的所有改动都挂在会话自己的作用域（`agent.ctx`），
  不改全局 profile，不影响其它会话。插件卸载 / 会话结束时自动清理。
- **不可逆操作**：归档旧会话默认开启，但执行前必须确认。命令行走 `--yes`，
  面板走确认对话框，两者都不确认就保留旧会话（其余步骤照常完成，报告标注「旧会话未删除」）。
- **失败不丢东西**：若新会话建好了但导入失败，新会话与日志文件都保留，
  报告给出可手动完成的剩余步骤。重复执行同一会话不会产生第二个新会话——
  台账 `<数据目录>/migrations/<源会话ID>.json` 会拦住，并让你选择续跑或放弃。
- **不伪造成功**：团队协作开关在运行时探测不到时，面板里置灰并说明原因，
  报告里如实记「未启用 + 原因」。
